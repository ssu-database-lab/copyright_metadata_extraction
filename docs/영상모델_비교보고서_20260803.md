### 2-3. 프레임 추출 (구현계획서 §3과 동일 설정)

```bash

  -ss "$T" -t 2 -i "$VIDEO" \
  -vf "thumbnail=n=30,scale=768:768:force_original_aspect_ratio=decrease" \
  -frames:v 1 -q:v 3 -y "frame_%02d.jpg"
```

길이별 목표 프레임 `<10s→3 · 10~60s→5 · 1~5m→8 · 5~15m→12 · 15m+→16` (하한 2장), 1.75배 오버샘플 후 dHash(8×8) 해밍거리 >6 으로 중복 제거.

**시사점:** 저작물명·인물명은 **VLM이 채워서는 안 되는 필드**다. `work_title` 은 파일명·DB에서 가져오고, VLM 출력은 `description`/`keyword` 에만 반영해야 한다.

### 4-2. 언어 일관성

`qwen3.6-35b-a3b` 는 한국어 프롬프트에도 영상 C에서 키워드 전체를 영문으로 반환했다 (`Popeye, Bluto, Olive Oyl, Halloween, Classic Cartoon, Comedy, Animation`). 다른 7개 모델에서는 발생하지 않았다. 경량 모델 채택 시 **언어 강제 후처리가 필요**하다.

### 4-3. Gemma는 영상에서 경쟁력이 없다

이미지 트랙의 현행 모델이지만 영상에서는 **76.9% / 20.2초** 로, 1위 모델보다 **덜 정확하면서 4배 느리다**. 다만 영상 C는 6/6으로 만점이었고 토큰도 가장 적다(7,451 — 프레임당 280토큰 고정). **이미지 전용으로 유지**하고 영상 1순위에서는 제외한다.

### 4-4. 추론형 모델의 비용·지연 구조

입력 토큰은 8개 모델이 거의 동일하다(7.4k~10.5k — 프레임이 지배). 반면 **출력 토큰은 629~5,271로 8배 차이**가 난다. `qwen3.6-plus`(5,271 tok, 28.0초)와 `qwen3.6-35b-a3b`(3,691 tok)의 지연은 추론 토큰에서 발생하며, **정확도 향상으로 이어지지 않았다**(84.6% / 76.9%). 메타데이터 추출에는 추론형이 유리하지 않다.

## 5. ⚠️ 시험 하니스의 프레임 샘플링 편향 (계획서 설계와 불일치)

채점 과정에서 확인된 사항으로, **구현계획서의 설계 결함이 아니라 본 시험 하니스가 그 설계를 따르지 않은 문제**다.

| 영상 | 길이 | 마지막 프레임 시점 | **관측 구간** |
|---|---|---|---|
| A 반찬 | 7.0s | 3.5s | 앞 **50%** |
| B 튤립 | 61.7s | 46.3s | 앞 **75%** |
| C 뽀빠이 | 380.4s | 208.3s | 앞 **55%** |
| D 마을 | 14.0s | 2.6s | 앞 **19%** |
| E 야경 | 16.3s | 9.2s | 앞 **56%** |

**5개 영상 전부**가 뒷부분을 보지 못했다. 원인은 하니스가 쓴 **탐욕적 순차 선별의 조기 종료**다.

```python
for t, f in raw:                      # raw 앵커는 영상 전체에 균등 분포
    if all(ham(d, dhash(k[1])) > 6 for k in kept):
        kept.append((t, f, d))
    if len(kept) >= target: break     # ← 목표치 도달 시 중단 → 뒤쪽 앵커 미도달
```

앵커 자체는 전 구간에 균등 배치되지만, 앞에서부터 순회하며 목표 장수를 채우면 즉시 멈추므로 **뒤쪽 앵커는 추출조차 되지 않는다**. 영상 D는 여기에 더해 느린 팬 촬영이라 dHash 중복 제거가 전 프레임을 걸러냈고, 하한 2장 규칙이 **가장 이른 두 앵커**(0.9s·2.6s)를 선택해 14초 영상의 앞 19%만 남았다.

### 계획서 설계는 이 문제를 이미 회피하고 있다

구현계획서 §3-4는 선별 구조를 다음과 같이 규정한다:

> **구조**: 목표의 **1.75배 오버샘플 → 품질필터 → farthest-point(max-min) 다양성 선별 → N장**

**farthest-point 선별은 오버샘플 집합 전체를 후보로 놓고 서로 가장 먼 프레임을 고르므로 시간축 앞뒤에 고르게 분포한다.** 반면 본 시험 하니스는 이를 구현하지 않고 탐욕적 순차 방식으로 단순화했다. 즉 **계획서를 수정할 것이 아니라, 구현 시 계획서 §3-4를 문자 그대로 따르면 된다.**

**영향 범위:** 8개 모델 모두 **동일한 프레임**을 받았으므로 **순위 비교는 유효**하다. 다만 절대 정확도는 **하한값**으로 보아야 하며, §3-4대로 구현하면 전 모델의 점수가 오를 가능성이 높다.

**구현 시 확인 사항:**
1. §3-4의 farthest-point(max-min) 선별을 실제로 구현할 것 — 탐욕적 순차 선별로 대체하지 말 것
2. 하한 2장이 적용될 때는 앞 2장이 아니라 **처음과 끝**을 선택할 것
3. 영상 D처럼 중복 제거가 과도한 경우를 위해 dHash 해밍거리 임계값(현재 6) 재검토
4. 위 3개 반영 후 동일 5영상 재측정 → 절대 정확도 갱신

나머지 4개 모델은 공식 단가를 확인하지 못해 **금액을 산정하지 않았다**(토큰 실측값만 §3에 제시).

**Gemma → omni-plus 전환 시 증가분은 영상 1건당 ₩1.74**다. 구현계획서 §1의 건당 총원가 **₩96**(계약서 5p + 영상 1건) 대비 **+1.8%**이며, 비용은 통합검증 단계(₩35.4)가 지배하므로 **모델 선택의 판단 기준이 되지 못한다**. 정확도 15.4%p 개선(76.9% → 92.3%)이 이 금액보다 훨씬 가치가 크다.

환율 $1 = ₩1,400 (비용산정서와 동일).

## 7. 결론 및 권고

### 7-1. 영상 트랙 모델 체인 (변경)

```
1순위  qwen3.5-omni-plus              92.3% · 5.0초 · ₩2.01
2순위  qwen3-vl-235b-a22b-instruct    80.8% · 4.0초 · ₩1.51   (OCR용으로 이미 스택 보유)
3순위  google/gemma-4-31b-it          76.9% · 20.2초 · ₩0.27  (이미지 트랙과 공유)
```

폴백 2순위를 `qwen3-vl-235b` 로 둔 이유는 정확도 4위이면서도 **가장 빠르고(4.0초)**, 이미 OCR 단계에서 검증된 모델이라 신규 의존성이 없기 때문이다. Gemma는 이미지 트랙에서 계속 쓰므로 최종 폴백으로 유지한다.

### 7-2. 한계 — 이 결론의 신뢰 범위

- **표본이 작다.** 영상 5건 · 26항목이다. 1·2위 격차(24 vs 22항목)는 **2항목 차이**이므로, 표본이 바뀌면 순위가 뒤집힐 수 있다.
- **하니스의 프레임 편향이 있는 상태의 측정**이다(§5). 계획서 §3-4대로 구현한 뒤 재측정이 필요하다.
- **자동 채점의 한계** — 부분문자열 매칭이라 문맥상 오답도 적중 처리될 수 있다.
- **오디오 미반영** — 전 영상이 오디오를 보유하지만 프레임만 전송했다. ASR 트랙은 구현계획서 §5에 따라 1차 제외 상태다.

따라서 본 결론은 **"omni-plus를 1순위로 구현을 시작하기에 충분한 근거"**이지, 최종 확정이 아니다.
